## 1. 产品目标与需要守住的边界

### 1.1 用户真实需求

1. 本地文件散落在多个盘符和目录，**整理或搬运它们的成本高于收益**；Looma 应通过 Reference Mode 组织它们，而不是强迫用户重构文件夹。
2. 玩过游戏、看过动漫、完成项目、产出 RVC 模型/音频，很多重要经历即使没有截图、视频或准确日期，仍应留下可回顾的**个人足迹**。
3. 作品、实体、目录、资产、Memory、Experience、Collection 的关系必须自然，但用户**不应该理解数据库模型才能完成操作**。
4. 日后卸载游戏、移动硬盘离线、路径改变或取消追踪，**不应该连带抹去通关经历、项目记忆和作品档案**。
5. PC 端 Antigravity、DSH / 小满 / 阿醒等外部 AI 是授权消费者，经 CLI / MCP 使用 Looma；**Looma 不需要内置聊天大模型**，也不要误以为 PC stdio MCP 天然可以直接远程服务手机。
6. 希望逐渐形成无需每日维护的长期档案。少量准确而有意义的记录，优于大量需要人工修补的元数据。

### 1.2 不可退让的底线

- Local-first；不将真实媒体文件转移、复制、改名或上传为默认操作。
- Archive / Untrack / Delete relationship / Physical Delete 是不同操作；常规 UI 不暗示会删除原文件。
- 足迹必须能独立于实体文件的在线状态存在。拒绝扫描器根据文件离线状况推断用户“从未玩过”。
- 数据可导出、验证并恢复；任何改进不得以破坏旧 Vault 为代价。
- 不将“功能越多”作为成功定义；性能、低操作成本、搜索找回能力和信任更重要。

### 1.3 本次不应假设的事情

- 截图能证明**界面出现了什么**，但不能证明后台数据库没有实现对应功能。
- README 的“已实现”说明不是运行时验收；具体逻辑仍应以源码、测试和用户操作为准。
- 截图顶部出现 `v0.2.0` 不足以断言用户在运行旧程序；可能只是 VaultInfo / 前端展示版本不一致。
- 工作区当前 `master` 的确切 SHA、用户实际运行的 `Looma.exe` 对应 SHA，**必须由反重力自行核对并写入报告**。

## 3. 公开源码抽查：我已看到的事实与需要确认的地方

> 本节是基于公开 `master` 原始文件的抽样阅读，非完整编译与调用链审计。请反重力以本地 `git rev-parse HEAD` 的真实代码逐条确认或纠正。**特别注意：先确认用户运行的 EXE 是否包含这些代码。**

### F-01｜`Work` 当前主要以 `Entity.properties.work` 存储

- 线索：`crates/core/src/models/work.rs` 里的 `WorkMetadata`、`Entity::new_work()`，以及 `WorksView.tsx`、`GamesView.tsx` 都调用 `list_works`。
- 初步判断：作品页与游戏库至少**在读取层**复用 Work / Entity 模型；但创建、更新、候选确认、显示进度及资料编辑可能是各自实现的 UI 流程。
- **待确认：**是否存在同一游戏两个 Work ID、某处维护的是 Entity 通用属性、另一处维护 WorkMetadata 的可能？

### F-02｜实体编辑存在“嵌套 JSON 变成字符串”的高风险线索

- 路径：`apps/desktop/src/components/EntitiesView.tsx`。
- 读取：编辑时 `Object.entries(entity.properties)`，对象值 `JSON.stringify(v)` 放入输入框。
- 写入：保存时 `propertiesObj[trimmedKey] = value.trim()`，没有明显按原类型解析回 JSON。
- 显示：实体详情对属性使用 `String(v)`，对象会成为 `[object Object]`。
- **这不是单纯的排版问题：**若用户用实体通用编辑器修改游戏实体，`properties.work` 有可能从对象变成字符串，并破坏 Work 解析。必须优先隔离复现；如果存在不同代码路径的校验或修复，请提供证据。

### F-03｜`list_assets` 的前后端分页参数契约可能不一致

- 前端：`apps/desktop/src/App.tsx` 调用 `invoke('list_assets', { limit: 50, offset: 0 })`。
- Tauri：`apps/desktop/src-tauri/src/lib.rs` 中为 `list_assets(filter: Option<AssetFilter>, ...)`。
- `AssetFilter` 定义在 `crates/core/src/models/asset.rs`，含 `limit`/`offset` 字段；数据库仅在 `filter.limit` 有值时添加 SQL `LIMIT`。
- **注意：**不能据此直接断言“只加载 50 条”。反而有可能因为缺少 `filter: {...}` 这个包装，前端提供的 `limit`/`offset` 被忽略，导致实际执行无上限查询。
- **待确认：**Tauri 参数转换的真实行为、默认 limit、首页/资产页/时间线/全局搜索对同一数据集的依赖，以及 1 万/10 万文件时的内存上限。

### F-04｜当前资产列表卡片并不绘制图片内容

- 路径：`apps/desktop/src/components/AssetsView.tsx`。
- 卡片网格直接渲染 `getKindIcon()`；只有打开图片详情时，才调用 `read_asset_preview(path)`。
- IPC：`apps/desktop/src-tauri/src/lib.rs` 的 `read_asset_preview` 会读取原始文件（30 MB 上限）并将完整字节编码为 Base64 data URL。
- **待确认：**是否存在别处实现的 ThumbnailService / 缓存 / 异步预览？当前预览是否可能带来性能、内存与任意路径读取问题？是否能在不复制原件的前提下生成小型、可重建的缓存？

### F-05｜游戏进度可能过度使用“章节”模型

- 路径：`apps/desktop/src/components/GamesView.tsx`。
- `handleQuickStepProgress()` 调用 `update_work_progress`，固定 `positionType: 'chapter'`。
- 完成状态会弹出足迹录入框，默认日期为当天、平台为 PC；`GamesView` 已有体验记录区域。
- **待确认：**一般单机、模拟器游戏、章节制游戏、二周目、白金/全成就、只想标记通关，这些场景是否能自然表达？作品页是否拥有等价能力？默认日期是否会误导用户把历史通关补录成今天？

### F-06｜时光轴已有 Experience 类型，但仍按统一时间戳聚合

- 路径：`apps/desktop/src/components/TimelineView.tsx`。
- UI 已存在 `selectedType: 'experience'`，并调用 `query_timeline`；查询失败时基于客户端现有数组拼接回退。
- 年份分组使用 `new Date(item.timestamp)`；附件中当前显示的大多数是收录/文件时间。
- **待确认：**在不损坏原始数据模型的前提下，是否应区分 “经历/回忆” 与 “系统活动/资产收录” 两类时间线？`occurred_precision=unknown` 或 `year` 的条目如何分组？查询失败时显示截断的模拟结果是否构成误导？

### F-07｜智能建议的“批量应用”可能发生部分成功却显示整体成功

- 路径：`apps/desktop/src/components/InsightsView.tsx`。
- `handleBatchApplyHigh()` 筛选 `confidence >= 0.85` 的关联及聚类建议，然后逐条 `safeInvoke('apply_smart_suggestion')`。
- `safeInvoke` 对错误返回 `null`；批量循环没有明显聚合失败结果，却会设置整体成功反馈。
- **待确认：**后端是否幂等、是否有逐项审计与撤销路径、置信度的业务含义是什么？未来是否真的需要自动批量执行，还是先以“解释建议 + 用户确认”为主？

### F-08｜多处 `safeInvoke` 把 IPC 错误转成 `null`

- 线索：`App.tsx`、`WorksView.tsx`、`GamesView.tsx`、`AssetsView.tsx`、`InsightsView.tsx`、`TimelineView.tsx`。
- **待确认：**这些页面在真实桌面端出现数据库错误时，是展示错误状态、静默空白、还是落入演示数据？用户能否判断数据没有加载，而不是误认为资产库为空？

### F-09｜顶部版本字符串与实际应用版本的来源

- 线索：`App.tsx` 模拟 VaultInfo 中硬编码 `0.2.0`；`HomeView.tsx` 在获取不到版本时也回退到 `0.2.0`。
- **待确认：**实际 `VaultInfo.version` 是数据库 schema、Core 版本、软件版本还是 Vault 格式版本？是否应分别展示 Desktop App / Core API / Vault Schema？打包后如何追溯 SHA？

### F-10｜数据库并发边界已经在代码注释中明确

- 路径：`crates/database/src/db.rs`，`LoomaDb` 使用 `Arc<Mutex<Connection>>`，注释声明**保证的是同一进程内同步**，独立桌面/CLI/MCP 进程并发写入不在当前保证范围内。
- **待确认：**个人长期使用时是容忍偶发 SQLite Busy、推荐单写进程，还是需要进程间协调？不要在 UI 优化名义下突然引入复杂服务架构，先给真实冲突概率和最低成本解决方案。

## 4. 希望反重力优先回答的 12 组代码级问题

**每组必须输出：**当前行为、最短调用链、源码路径/函数/行号、是否存在复现证据、对用户的影响、可选方案 A/B（及大致复杂度）、推荐与反对理由。无法证实时明确说“未验证”。

### Q1. Work、Game、Entity 究竟是什么关系？（领域身份 / 单一真相源）

- 作品和实体是否同一条 `entities` 记录？游戏库是过滤视图还是还有独立持久化关系？
- 一次创建游戏候选确认后写哪些表？目录路径、别名、封面、`WorkMetadata` 的身份怎么建立？
- 同一个游戏在 E/F 两盘有两份，或同时有模拟器本体、ROM、补丁、存档，系统目前识别为一个 Work 还是多个？
- 当用户从通用实体编辑器修改作品时，是否能破坏 `work` 结构？
- 哪些字段属于 Work 的规范数据，哪些只是展现层衍生？同名作品和不同发行版本如何避免合并错误？
- **讨论选项：**保留两个独立导航入口但共享一个 Work Detail；合并游戏库为作品页筛选；或根据使用数据保留游戏专用工作区。哪个用户操作最短？

### Q2. 是否存在编辑器导致的结构化属性损坏？（高风险待复现）

请使用临时 Vault：创建含嵌套 `properties.work.progress` 的游戏 → 用实体概念页面仅修改描述 → 保存 → 重新读取 `get_work_summary`。

应记录保存前后的 JSON 类型，并回答：

- 对象是否变成 JSON 字符串？嵌套字段是否整体覆盖？
- 如果存在，该入口应只读展示 Work 内部字段、提供专用表单，还是引入类型感知通用编辑器？
- 更新是否应采用字段级 Patch、版本号/乐观并发或明确白名单，而非全量覆盖？
- 历史测试数据是否已出现类型被污染？**只读检测，不自动修复真实数据。**

### Q3. 大规模资产的加载、分页、搜索是不是同一套真实路径？

- 请核对 `App.tsx` 的 `list_assets` 参数与 IPC 的 `filter: AssetFilter` 契约，展示真实序列化参数和结果。
- 当数据库有 1K、10K、100K 资产，启动时读取多少？页面内搜索是在前端数组还是 DB/FTS？`GlobalSearchModal` 是否使用相同的查询？
- 切换页面、扫描刷新时是否重新查询所有资产并阻塞 UI？
- 时间线的 fallback 是否将“前 50 条”误表现成完整历史？
- **讨论选项：**分页游标、按页独立请求、后端过滤、虚拟列表、缓存失效策略；优先哪个最小方案？

### Q4. Reference 图片预览怎样才真正好用？

- 除图片之外，视频封面、音频波形、PDF 首屏、3D 文件是否都应支持？MVP 先做什么？
- 目前读取完整文件转 Base64，面对 8–30 MB 大图、1 万图册成本如何？
- 是否已有可复用媒体缓存/Hash/索引？
- **讨论选项：**A. 列表小尺寸缩略图 + 详情原图；B. 系统预览壳；C. 先只改善图片；比较依赖、可维护性、源文件隐私。
- 缩略图缓存放哪里？如何限制磁盘占用、清理失效缓存、保留离线目录中的历史预览而不造成误导？
- 永远不因“生成缓存”把整份媒体搬进 Managed 资产模式。

### Q5. 个人足迹、状态进度和 Memory 之间怎样划界？

围绕四种真实输入：

1. 《血源诅咒》最近通关，**没有录像、没有截图、实际日期未必准确**。
2. 一部动漫看到了第 12 集，今天只是正常追番，不想写日记。
3. 一款游戏二周目再次通关；此前的首次通关不能被覆盖。
4. 一个 Rust 项目发布新版本，需要保留提交/文档链接和一句经验总结。

请解释：

- `Work.status` 与 `ExperienceEntry` 是否允许独立编辑？能否“Completed 但没有足迹”？
- 一次用户动作应生成几条数据库记录、几条时间线事件？
- 记忆/感想应嵌在 `Experience.note` 还是创建独立 Memory？什么情况下选哪个？
- 日期未知时是否允许创建并在时间线单独分组？
- 游戏、动漫、书、项目是否真正共用 Experience 领域服务，还是只有 GamesView 开放了 UI？
- **最优目标：两次以内点击完成一次有意义的足迹记录，且不能强迫补图或写评语。**

### Q6. 时间线的“事实时刻”怎样定义？

至少辨析四类时间：

- `asset.modified_at`：文件系统修改时间（可能是从网络下载/复制时带来的旧时间）。
- `asset.indexed_at`：Looma 第一次或最近一次扫描收录的时间。
- `entity.created_at` / `memory.recorded_at`：档案登记/笔记记录时间。
- `experience.occurred_at`（含 year/month/day/unknown）：用户经历的发生时间。

请讨论：

- 应否有“个人经历”与“系统活动”两种时间线？建议默认哪个？
- 未知发生日期的历史足迹，应该显示在哪一组，而不是伪装成今天发生？
- 同一次扫描进来 10 万文件，是否会让有意义的个人经历完全被淹没？
- 用户在未来回顾“2026 年我通关了哪些游戏”时，目前 FTS、年份筛选和时间精度能否支持？
- **请产出两套可比较的线框/交互流程**，而不是直接改动 Timeline。

## 7. 真实任务验证：请用可复现脚本，而不是“感觉体验良好”

所有任务先使用临时 Vault。现有截图只有 3 个 Asset、2 个 Entity、1 个 Memory、1 个 Work，这些数据太少，不足以证明长期使用性能。

### 场景 T-A｜《血源诅咒》通关补录

**输入：**没有对应本地游戏文件，没有截图，日期不准确，只有“最近通关，PC 模拟器”这个事实。

**目标：**用户在 GUI 中能建立或找到作品 → 标记 Completed → 创建一条 `completed` Experience → 在个人足迹中看到它 → 归档作品后仍可搜索与回顾。

请测量：点击数、必填字段数、是否强制填今日日期、是否重复创建作品、是否会误生成两条足迹。

### 场景 T-B｜散乱壁纸目录

**输入：**临时复制/生成约 1K/10K 张多尺寸图片作为测试集，模拟路径包含中文、空格、特殊字符、重复文件名和离线盘。

**目标：**扫描 → 找到一张特定壁纸 → 预览 → 关联集合 → 原目录不变 → 离线后能说明状态，重新上线可恢复引用。

请测量：扫描耗时、UI 首屏时间、峰值内存、列表中找图耗时、缓存大小和可能的误判。

### 场景 T-C｜开发项目 + RVC 文件

**输入：**一个项目 GitHub 链接、一个模型权重、一个音频源、一份输出、一次重要版本记录。

**目标：**在不建专用“RVC App”的情况下，凭项目或作品名检索出相关 Asset、ExternalReference、Memory/Experience 与 Relation。

请测量：建立关联的实际操作次数；是否需要重复录入同一个实体；是否可以按关系反向找回。

### 场景 T-D｜存量资料迁移与数据恢复

**输入：**一份从旧版本升级的隔离 Vault，含多个 Work、Nested JSON、SourceRoot、Archive、Untrack、Experience、外链及合集。

**目标：**升级 → 新 UI 正常读取 → 导出 → 在隔离新 Vault 恢复 → 比较关键对象 ID 与关系一致性。

重点比较：新/旧界面入口是否修改了 JSON 结构；是否因为界面调整造成旧数据不可见或被覆盖。

### 场景 T-E｜智能建议部分失败

**输入：**三条建议，第 2 条人为注入失败。

**目标：**用户能明确看到成功数、失败项、实际写入对象；重复点击不额外污染数据库。

## 8. 初步体验提升假设：优先“减少理解成本”，不优先堆功能

这些是**建议方向，不是确定开发需求**。反重力需要逐项提出支持/反对证据。

1. **Work 为“作品身份”，Asset 为“文件实物”，Experience 为“事件经历”，Memory 为“主观笔记”。** 在 UI 用自然语言表达，隐藏 `Entity.properties.work` 等内部实现名。
2. **同一作品只有一个可维护的主详情。** 游戏库可保留游戏专属视图，但不应该与作品档案形成两套冲突编辑规则。
3. **文件目录名只是自动识别线索，不是永久的作品标题。** 显示名、原名、别名、版本和路径须能分辨；自动建议不要静默重写。
4. **本地图片优先提供缩略图；其他媒体逐步评估。** 不搬动原文件、不做无界限 Base64 大图全量加载。
5. **时间线中“生活经历”优先于“索引操作”。** 系统活动有价值，但不要占领默认的个人回顾视图。
6. **归档只改变可见性，不抹除历史；Untrack 仅解除资产索引。** 用户始终能知道实际影响范围。
7. **MCP 只读优先，写入必须能向用户解释和审计。** 不因自动化带来新的数据污染。
8. **失败应当是明确的失败。** SQLite 锁、IPC 错误、部分成功、不完整搜索都不能用“空结果”掩饰。
9. **首页是入口而不是监控大屏。** 若 4 个统计数字足够有用，也可以保留；先测真实任务，不迷信卡片布局。
10. **小规模真实使用比继续做十套抽象更重要。** 建议先检验通关补录、壁纸找回、项目素材找回和恢复四条闭环。

## 9. 风险、非目标与可能被忽视的反例

反方评审必须覆盖以下问题：

- 更好的自动识别会不会**错误合并不同发行版本或同名游戏**？
- 更便捷的 Entity 编辑器会不会引入对未知扩展属性的**类型擦除/静默丢字段**？
- “删掉游戏文件但保留通关记录”与“彻底删除含敏感信息的私人笔记”是否需要不同的用户操作？
- 缩略图缓存是否会泄露原本离线或用户已 Untrack 的文件内容？缓存是否默认可重建、可清空？
- 当数据达到 10 万条时，首页快捷卡片是否暗中造成全量扫描或查询？
- UI 合并是否会让游戏候选扫描、多盘位置和二周目足迹反而更难找到？
- 单机 CLI/MCP/GUI 多进程同时写时是否有数据一致性风险，是否需要提醒并限制写入？
- 未知日期的回忆如果都在“日期未知”分组，是否影响回顾？是否可以按“录入时间”查询但明确标识？
- “自动智能整理”如果带来错误关系的修复成本，会不会比手动维护更糟？
- 是否真的需要改所有页面？是否可能只修几个**高频真实流程**就足以明显改善体验？

本轮明确**不规划**：强制搬移资源、全媒体自动整理、自动录屏、按游戏独立建新数据库、内置聊天模型、全量云同步、插件市场、海量社交功能、自动后台读取用户私人目录。

不要用二十个琐碎选择题打断用户。反重力先自行分析，最后**最多列出 5 个真正影响产品方向的选择**，供用户和 GPT 共同讨论。

---

## 11. 向反重力强调的证据标准

- 代码引用精确到**文件路径 + 函数 + 行号**，如本地行号变化请以实际 SHA 为准。
- 不用“应该有”“看起来已经实现”“100% PASS”替代复现证据。
- 区分：截图可见、源码可见、测试覆盖、真实任务验证、尚属推断。
- 不要只报告测试总量；必须说明测试**是否覆盖正常 GUI 入口**，与用户行为一致。
- 对可能造成数据破坏的操作：只在临时 Vault 做最小复现；不得对真实 `C:\Users\...\AppData\Roaming\looma` 下数据试删。
- 可以指出本文建议的错误，并提出**更轻、更少抽象、更省维护成本**的替代方案。
- 如果仓库中功能已实现但 UI 不可发现，应标为**可发现性问题**，不是“功能缺失”。
- 如果代码行为只在 Web Demo 生效，必须与真实 Tauri EXE 分开报告。

---

## 12. 本轮讨论希望最终回答的 6 个决策问题

1. **Looma 当前最妨碍真实使用的前三个问题是什么？** 请按证据排序，而不是按视觉冲击排序。
2. **是否存在必须在导入真实长期数据前先修的风险？** 尤其是结构化属性擦除、列表边界、静默失败或错误写入。
3. **Work/Game/Entity 应该如何降低用户认知成本？** 是合并入口、共享详情，还是维持现状？
4. **如何让“通关一款游戏”和“找一张壁纸”两件事非常简单？** 它们应该成为首批真正产品级闭环。
5. **哪些能力在 v0.5 不应该做？** 请指出那些技术上酷但对用户日常价值低的项目。
6. **如果只允许做 2～3 个可回滚的小 PR，哪几个最值得做？** 附假设、验收标准和失败时的退出策略。

---

## 13. 本轮结束条件（讨论结束，而非代码完成）

收到一份有代码证据的讨论反馈后，再由用户与 GPT 完成以下决策：

1. 确认实际 P0 数据风险及是否需要先单独修复；
2. 确认 v0.5 的**最小产品价值范围**；
3. 确认 Work/Entity/Experience/Asset 的权威边界不会被 UI 改动破坏；
4. 确认 3～5 个真实任务的产品验收方式；
5. 最后才产出可以直接执行的 `v0.5 Implementation Plan`。

**在此之前，不要把这份 RFC 误认为开发任务列表。**

> **Looma 的最终目标不是“把磁盘整理成整齐的文件夹”，而是让用户无需整理，也能找回自己的数字资产与经历；甚至几年之后还能回答：“那时候我玩过什么、完成过什么、留下了什么？”**
