## 0. 一页纸总裁决

### 0.1 Looma 是什么

Looma 应是 **Local-first、用户拥有、Reference-first、外部 AI 可通过 MCP 访问的长期个人数字资产与经历档案**，而不是一个迫使用户整理硬盘目录的文件管理器，也不是自带 AI 聊天框的超级应用。

**四个核心对象的语义不变：**

| 对象 | 负责什么 | 举例 | 哪些事不由它负责 |
|---|---|---|---|
| Asset | 原地引用的实际文件或目录 | `D:/壁纸/1.png`、游戏目录、RVC 模型 | 不决定游戏是否通关 |
| Work / Entity | 作品、项目等概念身份及当前状态 | 《血源诅咒》、一本书、LucidHeart 项目 | 不等于磁盘路径；不是历史事件 |
| ExperienceEntry | 真实发生过的一次个人经历 | 首次通关、二周目、项目发布 | 不等于当前状态；不要求附带媒体 |
| Memory | 主观文字与思考 | 评价、笔记、技术复盘 | 不替代可检索的作品身份 |

**主线：**保持文件原位 → 能找到 → 能理解属于什么 → 能留下一段人生足迹 → 有把握恢复。用户不应为使用 Looma 被迫做第二份“文件整理工作”。

### 0.2 核心产品决策（全部定案）

| 决策点 | 最终选择 |
|---|---|
| 作品页与游戏库 | **两个入口暂保留**；底层唯一 Work，同一详情组件，游戏页是游戏专用工作区。后续用真实数据决定是否合并菜单 |
| 时间线 | **双轨**：默认个人足迹/记忆，另有文件/系统轨；未知发生日期单列，不虚构日期 |
| 图片浏览 | **只实现图片缩略图**，异步、有界、本地可丢弃缓存，绝不碰原始图片 |
| 个人足迹 | 状态与历史分离，允许单独改状态、不强迫生成 Experience，历史补录不默认今天 |
| 资产 | Reference Mode 为默认；归档、Untrack、离线、删除原文件四种语义严格分离 |
| 元数据 | 现有 `Entity + properties.work` 模型保留；禁止普通 Entity 编辑器破坏 WorkMetadata |
| AI / Cloud | v0.5 不内置 LLM、不强制联网、不做同步；以后仍允许**可选**云端元数据备份 |
| 执行方式 | 五个小 PR，**先安全后体验**；全部可自动推进但每个 PR 独立可测试、可回滚 |

### 0.3 执行门槛（Stop-the-line）

出现以下任一情况，**停止后续 PR，不用自行猜测或跳过：**

1. 需要破坏性修改 `001~004` 历史 Migration；
2. 测试可能移动、覆盖或删除用户真实媒体；
3. 发现现有真实 Vault 存在不可兼容的数据结构，无法提供增量迁移与备份路径；
4. 未能实现可靠的写入冲突检测，却准备启用会覆盖其他进程数据的全量更新；
5. 备份恢复无法验证一致性或失败会污染原 Vault；
6. 某 PR 的核心用例失败，却试图通过隐藏异常、跳过用例或弱化断言来宣称 PASS。

## 2. 统一的工程总约束

### 2.1 单一业务门面

```text
Desktop ─┐
CLI ─────┼─> LoomaCore / application services ─> repositories / scanner / filesystem
MCP ─────┘
```

- 不得让修复后的 GUI 再次直接绕过 Core 修改 SQLite。
- 作品、Experience、Asset、Relation、SourceRoot、备份由现有核心服务掌握领域规则。
- 若现有 Core 已有可复用的 `search`、`update_work`、`Audit`，**优先扩展而不是创建另一套并行服务**。
- 新功能按小模块拆分；不以“架构整洁”为由重写已稳定的现有业务。

### 2.2 数据与 Reference 不变量

- 扫描、缩略图、搜索、归档、Untrack、Doctor **不得删除/修改用户原文件**。
- `Missing` 不等于磁盘离线，`Archived` 不等于删除，`Untrack` 不等于物理删除。
- Experience 即使没有对应本地文件仍可保存；文件失联后 Work 和历史足迹仍存在。
- 若需要新字段，可新增版本化 Migration（如 `005_xxx.sql`）；**不可修改已发布的 `001~004`**。
- 安全测试使用临时 Vault 和临时文件根目录，必须在代码中验证测试根路径，禁止指向真实用户文件。
- 不得将缓存文件视为用户数据：缓存应随时可删除、重新生成，不应进入标准长期备份。

### 2.3 失败必须显式

- 不得以 `let _ = ...` 吞掉影响业务结果的数据库错误。
- 不得 `catch → console.warn → null → empty state` 把读失败伪装成无数据。
- 需要向用户区分：加载中、真空状态、部分成功、失败、离线、未授权、冲突、格式不支持。
- 允许“部分成功”的任务须返回成功/失败/跳过数量、失败项与可重试性；若领域上要求原子性，必须事务化而不是只报告部分失败。

### 2.4 性能与兼容

- 所有大型列表查询均在 Core/数据库侧分页，不能让 React 根状态永久持有全量数据。
- 稳定排序必须带唯一 ID 作为并列排序字段，避免翻页重复/漏项。
- Windows 路径、中文、空格、大小写、盘符变更、离线移动盘、UNC 路径要有回归测试。
- 任何跨进程写入在 SQLite 层仍受事务、`busy_timeout` 和冲突检查约束；单进程 `Mutex` 不等于跨进程一致性保证。

## 3. PR 0A｜数据语义防线与智能建议正确性（第一优先级）

### 3.1 Entity 编辑问题的最终决策

**不采纳**“用户输入看起来是 JSON 就自动 `JSON.parse`”方案。

采用 **结构化领域保护 + 有类型的普通属性编辑 + 后端守卫 + 冲突检查** 四层约束。

#### A. 分类并保护字段（不要全局封杀名字）

- 只有**对应实体类型**才有对应系统保留字段。对于 Work，`properties.work` 属于领域层，任何通用 Entity 表单都不可直接修改或删除。
- `work` 内部的 `status/progress/aliases/cover_asset_id` 由专用 WorkService 处理；不能因为这些词与自定义 Entity 普通属性重名就一律禁止用户使用。
- 通用编辑器可以安全地修改实体 `title`、`description`、自定义普通属性；Work 内部结构显示只读摘要，并提供“打开作品详情”入口。
- 对已有未知/扩展属性必须**原样往返保留**；不能因为表单不理解就删除它。

#### B. Patch 而非全量覆盖

推荐新增或复用明确的命令（示意，不强制命名）：

```rust
struct UpdateEntityBasics {
    id: String,
    expected_revision: Option<i64>,
    title: Option<String>,
    description: Option<String>,
    custom_properties_patch: Option<Map<String, Value>>,
}
```

注意：以上 `Option` 只是说明意图，**实际接口必须能区分“字段未提供”和“明确清空字段”**；可用 `Patch<T>` / `Option<Option<T>>` / 明确 `remove_keys`，不要照抄导致无法删除字段。

- 服务层在事务内**重新读取最新实体**，只修改批准字段，保留全部未知/系统字段。
- 防止 Desktop 从旧快照提交，覆盖 MCP/CLI 刚更新的进度或别名。
- 优先使用可靠的 `revision` 乐观锁；若无版本列，可以在事务内对快照版本/哈希做等价校验。若需要新增 `revision` 列，使用 `005` 增量 Migration。`updated_at` 单独比较时须处理时间精度碰撞。
- 若预期版本过期，返回明确 Conflict，并展示“已有其他客户端更新，请刷新后重试”；**不得静默覆盖**。

#### C. Rust 侧强制保护

- `update_entity` / 专用 Patch 的公共路径要拦截非法的 `properties.work` 修改，即使它是**可反序列化但不被授权**的 WorkMetadata 也要拒绝。
- 合法 WorkService 内部写入仍允许更新 `work`，需通过受控内部 API 而不是绕过验证裸写。
- 对未传递 `work` 的合法普通编辑，在事务中从最新数据库保留该对象；不允许 `null` 或字符串抹去。
- 不要依赖前端只读 UI 作为唯一保护。CLI/MCP/旧客户端都必须受同一边界约束。

#### D. UI 数据类型

- String 始终是 String；Number、Boolean、Null、Array、Object 使用原生类型或专用编辑方式；**不猜类型**。
- Object/Array 默认摘要+只读，只有显式开启的 JSON 编辑器才能编辑被授权的普通自定义字段，并提供语法/类型验证。
- 渲染嵌套值使用可理解摘要（如 `进度：第 5 章`），不得出现 `[object Object]`。

### 3.2 智能建议的最终决策

- 85%、98% 等来自启发式规则的数值改为「精确同名」「目录关联」「名称相似」等**规则说明**；若保留内部 score，只用于排序，不能宣称统计置信度。
- `apply_suggestion` 必须真实执行才能返回成功。现有 Tag 建议若未实现，则不可应用并明确说明，不能返回 `Ok(true)`。
- Collection 加项失败必须传播或写入逐项结果；不得 `let _ = ...` 忽略。
- 批量应用由 Core 提供清晰语义：
  - **推荐**：`dry_run` 预览影响对象 → 用户勾选 → 执行 → 返回逐项结果；
  - 对相互独立项，允许部分成功，返回 `applied[] / failed[] / skipped[]`；
  - 对“一项创建合集并加入 N 个资产”的复合操作，要定义为一项原子业务动作，失败整体回滚或明确返回未完成状态，不得创建空合集却宣称完整成功。
- 批量重复点击要防重复（按钮 pending、必要的请求幂等键或查重）。
- 返回结果必须包含操作类型、对象 ID、错误原因；UI 不可无条件弹出“全部完成”。
- 审计日志记录成功变更。**不要求 v0.5 造一个通用 Undo/Redo 框架**，但错误操作必须可手动识别和修正。

### 3.3 PR 0A 必测用例

1. 用实体编辑器修改游戏标题、描述和自定义标签，重新读取 `WorkSummary`，进度/封面/别名/作品类型完全不变。
2. 从 Tauri/CLI/MCP 公共通道分别尝试提交 `properties.work = "string"`、`null`、合法但未授权的对象；均拒绝。
3. 旧客户端读取实体 A，MCP 修改作品进度，旧客户端再保存描述：**新进度不得被旧数据覆盖**；必须合并无冲突字段或返回 Conflict。
4. 原本 number/boolean/object 的自定义属性在编辑/保存后仍保持原类型。
5. 模拟建议中第 2 项失败，报告成功 1/失败 1 或整组回滚，UI 精确显示，不可显示全部成功。
6. Tag 建议没有实现时不能生成任何成功审计记录。
7. UI 详情不出现 `[object Object]`。
8. 测试前后真实用户媒体文件哈希不变（测试应仅对临时文件计算与操作）。

### 3.4 PR 0A 完成定义

**核心安全用例通过 + 实际 Tauri UI 修改一条测试游戏描述后游戏进度、别名不变 + 智能建议部分失败有明确错误结果。**

## 4. PR 0B｜分页、全库搜索、错误可见性与版本识别

### 4.1 分页的完整链路

之前调查显示 `App.tsx` 传 `{ limit, offset }`，Tauri 实际需要 `{ filter: {...} }`。请在当前 HEAD 用真实 IPC 证实是否已修复。

最终契约（示意）：

```ts
const page = await api.listAssets({
  filter: { kind: selectedKind, status: selectedStatus, limit: 50, offset: 0 }
});
const total = await api.countAssets({ filter: sameFiltersWithoutPagination });
```

- Core/SQLite **必须有上限**，不能只有前端 LIMIT；无过滤器时也不应默认无限制返回数万行。
- count 与 list 的过滤语义要一致；如涉及已归档、已 Untrack、Missing、Offline，明确计数范围。
- 标准排序：明确按时间/名称/ID 排，末尾追加唯一 ID 稳定排序；页切换、筛选变化要重置页码。
- 如果运行时数据频繁变更，普通 offset 分页可以作为 v0.5 简单实现；出现重复/漏项再评估 cursor，不要先过度设计。
- App 根状态只缓存首页必要的统计和轻量数据，不长期保存整个资产库。各页面按需查询。
- 首页统计来自聚合 `COUNT`/专用 Summary 接口，不以“当前已加载数量”冒充全库数量。

### 4.2 全局搜索必须绕开 React 已加载页

- `Ctrl+K` 查询后端全库，而非遍历当前 props。
- 统一搜索 Asset、Work/Entity、Memory、Collection；如当前已有 Core 搜索接口，必须复用并扩展，不要建两个语义不一致的搜索引擎。
- 返回统一的 `SearchResult {kind, id, title, subtitle, matched_field, ...}`；**只返回必要字段**，不要把整个文件/大 JSON 放进搜索结果。
- 支持精确名称、路径子串、别名与标题搜索、手记正文；FTS5 中文分词能力需实测，不能未经实现就承诺拼音检索。
- 若 SQLite LIKE 处理用户输入，正确转义 `%`、`_`、转义符，避免输入变成通配或误匹配；尽量使用参数化 SQL。
- 全局搜索响应异步防抖（可从 200~300ms 起步），防止旧请求晚返回覆盖新结果；并发请求应有序列号或取消机制。
- 任意搜索结果都必须能够导航到对应**实际详情**，不能只给一个文字提示。
- 搜索不能由于资产分页变成“只查到前 50 条”。

### 4.3 统一 API 错误处理，别把所有状态变成 null

推荐统一 `apiClient.ts`：

```ts
type ApiResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: { code: string; message: string; retryable: boolean; context?: string } };
```

- 区分：`loading`、`empty`、`success`、`error`、`stale`；列表错误时可保留旧数据并标记未刷新，而不是清空。
- 用户可读提示 + 开发者日志两条通道；日志不得泄漏密钥或不必要的本地敏感路径。
- 从一两个高风险页面开始迁移，然后其余页面分批迁移；旧接口不能随意混入假成功语义。
- Native Tauri 环境发生后端错误，**不能自动切到浏览器 Demo 假数据**；Demo 模式必须显式且界面可辨识。
- SQLite Busy、权限拒绝、文件离线、格式不支持，给用户可操作的提示（重试/重绑定/取消），不能统一显示“暂无数据”。

### 4.4 版本的三个维度

显示：**应用发布版本**、**构建 SHA（短）**、**Vault Schema Version**。可附 Core API 版本，但不要混淆。

- 应用版本来自打包元数据（Tauri/Cargo 统一）；构建 SHA 在编译时注入；Schema 从实际数据库迁移状态读取。
- `vault_meta.version = 0.2.0` 是历史数据时，应作为**Vault 自身历史元数据**解释，而不是直接显示为 App 发布版本。
- UI 标题/关于页只显示真实当前程序信息；版本信息读取失败应标为未知，而不是回退硬编码 `0.2.0`。
- 没有产品正式 release 的情况下，不必强行给最终用户显示内部开发代号 `v0.5`；可以使用 `0.5.0-dev+SHA`，但与实际版本文件一致。

### 4.5 PR 0B 必测用例

1. 临时 Vault 构造 10,000 个资产，真实 IPC 首次请求不超过设定 page_size，并验证 `count_assets` = 10,000。
2. 搜索第 9,999 条资产；即使第一页没加载也必须能命中并跳转。

4. 修改筛选后翻页，不重、不漏（稳定排序）。
5. 注入 SQLite Busy/文件权限错误：页面显示错误与重试，不呈现虚假空态。
6. Demo 与 Native 模式区分准确，不返回伪造的真实数据。
7. App SHA/发布版本/Schema 互不混淆。
8. 记录性能报告：冷启动、搜索 p50/p95、UI 渲染数量、内存峰值和测试设备；不以固定“毫秒级”未经测量的文案代替数据。

## 5. PR 1｜统一作品身份、详情与 Experience 补录闭环

### 5.1 Work / Game / Entity 最终关系

保持当前结构：

```text
Entity (Work identity, properties.work: WorkMetadata)
  ├── WorkDetails (作品档案通用入口)
  ├── GamesView (游戏专用快捷入口)
  ├── Relations -> Asset/ExternalReference
  └── ExperienceEntry[] + Memory[]
```

**不新增 works 表**。原因不是技术上不能迁移，而是当前收益不足以抵消复杂性；使用现有强类型 `WorkMetadata` 和 Core 服务足以实现目标。

- 作品与游戏页共享一个 `WorkDetailDrawer` 或同等功能组件。游戏页保留扫描候选、启动位置、周目等专有操作，不复制 Work 数据逻辑。
- 同一条 Work 只能有一个权威状态，修改后两页均能看到一致结果。
- 项目 Project Entity 不强行伪装为 Work；其关联文件、外链等复用现有 Relation 能力，以后可抽象公共 `SubjectDetail`，**不要现在要求重构全部实体**。

### 5.2 游戏候选与重复建档

- 自动从文件夹名推导的标题只是**建议**；创建前展示建议名与原始目录名。
- 原始目录名不必自动塞入作品 `aliases`（例如 `3DMGAME...CHS...` 可能包含发行组噪音）；它应该作为 **Source/目录资产上的原始标签或来源备注**保留。
- 标准标题与别名可由用户确认后加入 Work；不能静默删除“Remake、DX、完整版”等可能构成真实版本区分的词。
- 匹配现有 Works：先比较用户已确认的标题/别名，再列候选；提供「关联到已有作品」与「建立新作品」两个选择。
- **不自动合并两个 Work，不凭模糊匹配直接覆盖。** 检测到可能重复时提示候选及路径、平台等上下文。
- Work 可以存在而没有任何本地 Asset（例如《血源诅咒》模拟器版已卸载）。

### 5.3 Experience 与状态的交互契约

- `Work.status` 是当前概要；`ExperienceEntry` 是发生过的事件；`Memory` 是可选感想。三者各司其职。
- 改状态时可选“只修改状态”；明确点击「记录经历」才创建 Experience。
- 历史补录**不得预填今天为事实日期**。日期 UI 至少支持：精确日期 / 年月 / 仅年份 / 时间未知。`occurred_precision`、`occurred_value` 按当前模型严格存储。
- 如果用户明确选择“刚刚完成”，才可用本地今天作为默认值；存储时注意用户本地时区与 UTC 区别。
- 游玩平台默认为「未指定」，不应因为设备是 Windows 自动写为 PC；用户可选择 PC 模拟器、主机等实际情境。
- 不强制填写截图、时长、评语或章节；如果没有文件仍能建立 Work 和 Experience。
- 二周目、多周目是多条历史事件（新 request_id），不得覆盖旧记录；再次点击保存时沿用同一次提交的幂等键，防止双击重复。
- 如果事件语义要求同时修改 Completed 状态与 Experience，调用 v0.4 已有**原子复合事务**；如果用户选择只记录里程碑，则不能无理由强改状态。
- 游戏进度：消除硬编码「章」；不同类型使用可选的「章节 / 小时 / 百分比 / 自定义进度 / 不追踪」表达，不要求 v0.5 一次实现所有类型，但没有合适类型时宁愿显示「进行中」也不要错误显示“0 章”。

### 5.4 WorkDetailDrawer 最小布局

```text
┌──────────────────────────────────────────────────┐
│ 作品名称、封面/占位、类型、状态、别名、评分           │
│ [继续记录] [记录一次经历] [关联资产]                 │
├──────────────────────────────────────────────────┤
│ 历史足迹：开始 / 通关 / 二周目 / 完结 / 自定义        │
│ 可选：感想与 Memory 链接                             │
├──────────────────────────────────────────────────┤
│ 本地位置（可离线） | 外部链接 | 关联文件            │
├──────────────────────────────────────────────────┤
│ 高级字段（折叠，不鼓励直接编辑原始 JSON）             │
└──────────────────────────────────────────────────┘
```

### 5.5 PR 1 必测用例

1. 已有一条《血源诅咒》作品，无本地路径；补录“已通关，日期未知，PC 模拟器”，保存成功，两个入口均可访问。

## 6. PR 2｜图片缩略图与可靠资产浏览

### 6.1 仅做图片，不做重型媒体引擎

仅实现 JPG、PNG、WebP 等已支持解码图片的**按需缩略图**；不强行加入视频抽帧、PDF 渲染、OCR、3D/模型预览、全量图库 AI 分类。

### 6.2 缓存键与失效

反重力当前草案使用 `asset.id + modified_at.timestamp()`，**不够可靠**。

建议缓存身份包含：

```text
cache_key = H(
  asset_id,
  file_size,
  mtime_with_available_resolution,
  thumbnail_format_version,
  target_size,
  encoder_settings_version
)
```

- 不要求计算整文件 SHA-256 才能画缩略图，避免扫描几 GB 大文件的性能损耗。
- 同一秒内内容变化、文件系统 mtime 分辨率不同等可能导致碰撞；必要时加入文件身份、局部内容指纹、显式刷新/失效机制，不要宣称 `size + mtime` **绝对**保证新鲜。
- SourceRoot 重绑定但 Asset ID 与内容未变时可复用缓存。
- 缓存名只能由安全键生成，不能拼接不可信原始路径，避免目录遍历。
- 缓存路径属于 Looma 私有应用目录；**不得默认写在被扫描的外部原始文件夹中**。
- 生成文件先写 `.tmp` 再原子替换，避免多 worker/程序崩溃留下损坏 WebP。

### 6.3 后台工作模型

- 有界队列（可从 2~4 worker 起步，可按实际设备调优），仅处理当前可见页面 + 少量前后缓冲。
- 离开页面或切换筛选时，可取消或降低已不需要的队列优先级。
- 同一 Asset 的并发请求合并，避免重复解码。
- 解码需限制**像素尺寸、内存分配、耗时**，特别注意压缩小但像素极大的图片（decompression bomb）。
- 禁止因某张损坏图片导致整页加载失败；展示占位图和局部错误。
- 对超大、不支持、离线、权限拒绝的图片使用清楚的 fallback。
- 从原图解码后等比例缩至最大 320px；并非所有缩略图都必须 WebP，具体编码器由性能测试决定。
- 渲染选择受控的 Tauri 资源读取/自定义协议。若开放本地协议，**只允许 Looma 缩略图缓存目录，拒绝 `..`、符号链接逃逸和任意文件路径访问**。
- 原有 `read_asset_preview` 留给单项详情；列表绝不 N 次调用它读取几十 MB 原图。

### 6.4 缓存治理

- 建议缓存软上限 500MB，可调整；以实际总量统计、按最近访问清理；没有必要将每条缩略图都写入用户长期业务表。
- 用户设置页可查看缓存大小、清理缓存；清理后原 Work/Asset/Memory/Experience/Relation 记录全部不变。
- 缓存与 Reference 原件分离；移动盘离线时已有缓存**可以作为视觉占位**，但必须标注“原始文件当前离线”，不能误导为可打开原文件。
- 缓存不包含在长期 portable backup 中，不参与用户核心元数据恢复。

### 6.5 PR 2 必测用例

1. 100 / 1,000 / 10,000 张测试图片目录，首屏只请求当前页、当前视口图片；不会在启动时解码全库。
2. 缩略图命中缓存后不重复读取原图；修改原图后旧缓存按规则失效。
3. 同一秒修改、相同文件大小等极端条件有明确失效/刷新处理策略。
4. 一张恶意尺寸或损坏图片不能导致 OOM/崩溃，错误在单卡片可见。
5. 清理缓存不碰真实引用文件，且可以重建。
6. 断开移动盘仍能显示适当占位与离线状态；恢复后索引和 Work 关联仍完整。
7. 真实测量 CPU/磁盘/内存峰值、冷缓存和热缓存差异。**不能未经测量承诺内存 ≤150MB、所有图片 ≤20KB 或必定秒开。**

### 6.6 PR 2 完成定义

**用户可以通过图片内容而非文件名找到壁纸，且千级图片目录不会让界面明显失去响应或大量读取原图。**

## 7. PR 3｜个人时间线、信息架构与首页

### 7.1 双轨时间线：不要篡改历史时间语义

**默认：个人足迹 / 记忆**；辅助：文件 / 系统活动。

- 个人轨：`ExperienceEntry` + 确实属于用户记录的 `Memory`。Memory 若只有创建日期，必须注明“记录于”，不能假装“事情发生于”。
- 系统轨：扫描、Asset 新增/变更、Entity 元数据变更等技术记录。一次扫描上千文件，优先**汇总为一次扫描活动**，允许展开，而不是让每个文件占一条主时间线。
- **未知 occurred time**：归入“时间未详”，展示 `recorded_at` 用作解释，不放进某个具体年份/月日。
- 年份精度（如 2022）：归于该年份，显示“约在 2022 年”或“发生于 2022 年（仅知年份）”；不伪造月日、零点或时区。
- 年月精度归于对应年月；精确日期按用户输入的日历日显示，不擅自合成 UTC 日期时间。
- UI 过滤应传给后端查询，在分页之前执行。不得先取 50 条混合记录，再前端删掉文件记录，导致个人轨空白。
- 排序要分清 `occurred_at` / `recorded_at`；对未知时刻不通过同一个 timestamp 排序装成发生时间。
- 当数据库已有大量 Assets，按轨道查询必须有限分页与索引支持；禁止全表 UNION 后再把全部结果发给前端。

### 7.2 导航分组：小改而非全面重绘

保留现有所有能力，按用途分两组：

```text
日常
  首页
  我的作品
  个人游戏库（保留可见，功能复用）
  数字资产
  时光轴
  记忆手记

管理 / 高级（可折叠）
  集合收藏
  实体与关系
  智能建议
  系统设置
```

- 不删除已有模块或 URL/状态导航语义。
- 用户不必理解 Entity 才能记录 Work/Experience。Entity 作为高级图谱编辑入口，强调“高级使用”。
- 组件最大宽度应适应大屏（截图中内容集中于左侧，右侧留白明显），但不要通过拉长文本行破坏可读性。使用响应式网格和合理内容最大宽度。
- Home 不再主要展示技术宣言、SQLite KB、内部架构 Phase，而是提供“查找资产、记录经历、继续作品、数据健康”四个具体动作；技术信息下沉至设置/状态。
- 不新增大型 UI 框架；维持现有 React/Tailwind/i18n 体系。

### 7.3 PR 3 必测用例

1. 创建 3 条 Experience + 1 条 Memory + 2,000 条 Asset，个人轨仅显示个人经历和记录，不被 2,000 条资产刷屏。
2. 未知时间条目在“时间未详”，不会显示今天为发生日。
3. 精度仅为 `year=2021` 的事件没有伪造具体月、日、时区。
4. 轨道切换与年份过滤走后端，分页后结果正确，旧客户端数据可读取。
5. 导航新旧入口均能到达原有功能；多语言、暗黑/浅色主题与常见窗口尺寸无明显回归。
6. 首页快速入口真正导航到可执行任务，不做没有功能的装饰按钮。

### 7.4 PR 3 完成定义

**打开 Looma 默认看到自己的经历与接下来要做什么，而不只是数据库里有几条文件记录。**

## 8. 跨 PR 的横切问题（不用另造一个大工程）

### 8.1 备份恢复：以真实语义建立信任

反重力调查称 `0cb44b4` 已实现 Restore 单事务与 Manifest SHA-256 校验；执行时仍需做实际故障注入验证，尤其分清 **“备份包的完整性”** 与 **“恢复目标库状态的安全性”**。

最终要求：

1. **备份包描述**：明确写“只含 Looma 元数据、关联和手记等，不包含 Reference 目标的游戏/图片/视频原文件”。
2. **验证优先**：Manifest、校验和、Schema、引用关系预检必须在写入用户库之前完成。
3. **默认恢复到新的隔离 Vault**：这是面向普通用户的首选，不影响当前工作库。
4. **现有库合并导入**：保留为高级选项，清楚提示“按 ID 合并/覆盖同 ID 的记录，不等于回到过去的某个瞬间”。
5. **恢复前一致性快照**：使用 SQLite Online Backup API / `VACUUM INTO` 等受支持的方式；禁止直接复制正在有 WAL 写入的 `vault.db`。`VACUUM INTO` 的具体可用性和并发行为须实测，失败立即终止导入。
6. **禁止自动覆盖运行中的 DB 文件**：还原快照涉及关闭所有数据库连接、确认其他 CLI/MCP 进程停止写入、处理 WAL/SHM 与路径原子替换；v0.5 宁愿要求用户切换新 Vault，也不要做危险的“失败后直接复制快照覆盖旧 db”。
7. **恢复后验证**：比较对象数、关键外键、关系、Experience、SourceRoot、Untrack tombstones、样本记录与清单；缺失/失败必须显式告知。
8. **可测试**：构造损坏的 Manifest、缺失文件、JSON 损坏、恢复中途失败、数据库 Busy，证明原库不被污染。

**关于实施位置：**备份安全的核心行为不能只放在 `SettingsView.tsx` 按钮逻辑；要由 Core 提供规范化的 `validate_backup` / `restore_to_new_vault` / `create_consistent_snapshot` 或现有等效 API。若现状未覆盖，作为与 PR 0B 伴随的安全子任务，不要以 UI 文案替代可靠的恢复流程。

### 8.2 多进程状态可见性

- 当前 Desktop/CLI/MCP 独立进程，WAL + Busy Timeout 负责读写协调，不负责 React 缓存失效。
- v0.5 最低要求：外部 MCP 写入后，桌面页面可以通过**手动刷新/重新进入页面**可靠读到数据；不能因为全局状态长期缓存而必须重启程序。
- 可选增加焦点恢复时检查 `PRAGMA data_version`；**必须在同一持久 SQLite 连接上比较相邻读取值**，因为它是连接相关的变更计数，不能通过每次重开连接比较来判断变化。
- 不必开发新的 HTTP 远程服务、消息队列或复杂实时同步。
- MCP 仍默认 ReadOnly；写入由用户显式配置授权，不允许 PR 为方便 UI 直接提权。
- 手机小满/PC 阿醒的跨设备网关由外部已存在的桥承担，Looma 不内置跨互联网暴露的 MCP 服务。

### 8.3 SourceRoot、归档、Untrack 继续保持不变量

- SourceRoot 失联不能变成 Missing；重绑定应保持资产 ID 与 Experience / Relations。
- 扫描与缓存处理不应让已归档资产恢复 Active，也不应让 Untrack tombstone 被绕过。
- UI 在显示文件不可用时，区分离线、真实缺失、权限不足。
- 后续若允许“删除本地文件”，必须独立于本轮并进行新的安全评审；**v0.5 不提供原文件删除工具**。

### 8.4 对现有 CLI/MCP 和日志保持兼容

- 不因 UI 统一而破坏现有 CLI 命令与 MCP Tools/Resources；若必须调整结构，提供兼容层与回归测试。
- 不要通过原始 `Entity.properties` 直接暴露未经许可的全量数据给外部 AI；仍遵循 MCP 权限边界与审计规则。
- UI 的 API 错误报告避免输出整个 JSON 数据、用户路径或其他敏感信息到可外发日志。

## 9. 五个完整真实验收剧本（发布门槛）

### T-A｜《血源诅咒》通关补录

- 前置：空的测试 Vault；不提供游戏安装目录，不提供图片。
- 操作：创建/查找《血源诅咒》Work → 记录 `completed` Experience → 日期选未知或仅年份 → 平台设为 PC 模拟器（明确是用户输入）→ 可选写评语 → 保存。
- 结果：只有一个权威 Work；Work 与 Experience 同步可见；个人时间线不伪造发生日期；导出/恢复后足迹保持。
- 失败例：再次提交相同 request_id 不重复；另一次二周目采用新 request_id 保留多条记录。

### T-B｜壁纸与散乱图片目录

- 前置：测试目录包含中文、空格、同名不同路径、损坏图、超大图、不同尺寸 1,000 张及可选 10,000 条数据。
- 操作：Ref 扫描 → 翻页 → 查看缩略图 → 全局搜索未加载页 → 选择图片 → 归档 → 移动盘离线 → 恢复来源。
- 结果：原文件字节不变；缩略图按需生成，缓存可清除；搜索全库；归档/Untrack 状态正确；离线不误删。

### T-C｜开发项目与 RVC 物料

- 前置：临时 Asset 模拟 `.pth`、`.wav`、截图，Project Entity 与仓库 ExternalReference。
- 操作：关联到项目 → 从项目卡片反查物料 → 从 Asset 反查项目 → 对资料添加一条 Memory。
- 结果：不复制媒体；关系可检索；无须把 Project 强制建成游戏类型 Work；原始路径保留。

### T-D｜备份与恢复

- 前置：有 Work、Experience、Memory、Collections、ExternalReference、SourceRoot、Untrack 的混合测试 Vault。
- 操作：导出 → 校验 → 恢复到新 Vault → 对照对象数量、ID、关系与恢复后的查询行为；故意破坏包并尝试恢复。
- 结果：健康包完整恢复；坏包在写入前拒绝；原 Vault 没有任何额外修改；不会包含原媒体文件。

### T-E｜智能建议部分失败

- 前置：构造三个独立建议，其中一个目标不存在、一个 Tag 功能未实现。
- 操作：查看说明 → 预览 → 选取支持的建议 → 批量应用。
- 结果：成功/失败/跳过明确，禁用未实现操作，不会显示假 98% 成功率，审计正确。

## 10. 开发节奏、提交与报告协议

### 10.1 允许连续推进，但每个 PR 都必须“独立闭环”

```text
Preflight（确认 HEAD + 保护基线 + 临时 Vault）
  ↓
PR 0A  ── 测试与 UI 验收 ── Commit A
  ↓
PR 0B  ── 测试与 UI 验收 ── Commit B
  ↓
PR 1   ── 测试与 UI 验收 ── Commit C
  ↓
PR 2   ── 测试与 UI 验收 ── Commit D
  ↓
PR 3   ── 测试与 UI 验收 ── Commit E
  ↓
Final acceptance：五个真实剧本 + 备份/恢复 + 文档/二进制一致性
```

- 本文件已经给出总体产品决策。**不需要反重力每完成一个 PR 就回来请求 GPT 选择方向**；可继续实施下一包，前提是前一个包所有门槛满足。
- 如果某阶段遇到阻断项，则停止、回报关键事实、提供有限备选，**不能自己破坏安全约束强推**。
- 每个 PR 要有独立 Git commit，描述改变了什么；如用户没明确要求推送，可在本地提交与测试后按原有仓库工作流处理，不自动将有潜在安全风险的构建部署到真实 Vault。
- 禁止为通过验收而改测试预期、吞错误、删除旧用例。

### 10.2 每 PR 的交付模板

```md
## PR N 验收
- Git SHA / 工作树状态：
- 功能目标：
- 真实改动路径与关键调用链：
- 修复前复现步骤：
- 修复后测试命令 / 结果：
- 前端构建 / Release 构建：
- UI 手工验收剧本：
- 旧 Vault 兼容性：
- 数据与文件安全检查：
- 性能：硬件、输入规模、冷/热缓存、CPU/内存/耗时：
- 已知限制 / 后续事项：
- 阶段结论（PASS / PARTIAL / FAIL）：
```

### 10.3 性能基准的表达方式

- `10,000 条资产`、`1,000 张图片` 是**测试数据规模目标**，不等于必然能在任意 Windows 设备做到低于某个内存阈值。
- 记录真实测试条件：CPU、RAM、SSD/HDD、Windows 版本、Tauri/Node/Rust 构建、冷/热缓存、数据大小、搜索 p50/p95、首屏耗时和峰值内存。
- 先给测量数据，再根据实际设备确定性能门槛；不得杜撰“1 秒 / 150MB / 所有图片 15KB”结果。

## 11. 明确不做的事项

**v0.5 范围外：**

- 内置 LLM、聊天 UI、黑盒自主 Agent；
- 强制网络元数据刮削（可选外部元数据服务以后单独设计）；
- 云端实时同步、多设备冲突合并、远程公开 HTTP 接口；
- 动态插件市场和第三方插件安装沙箱；
- OCR、语义向量数据库、全量本地 RAG；
- 视频抽帧、PDF/3D 大型预览系统、录像、自动游戏监控；
- 自动搬移、重命名、整理或物理删除用户 Reference 原文件；
- 彻底重做数据库、强拆 `works` 表、重写 UI 框架；
- 完整通用 Undo/Redo 引擎、复杂消息队列与分布式事件系统。

**注意：**“v0.5 不做云备份”**不等于永远反对可选 Cloud Adapter**。长期目标仍是本地优先、用户可选的轻量元数据异地备份，与大型媒体文件不同。

## 14. 产品哲学：收束而不是继续堆功能

Looma 的下一个目标不是“更多表、更复杂的抽象、更多智能功能”，而是让普通的日常动作自然发生：

- 通关《血源诅咒》，即使没有截图、日期也记不清，仍然能留下真实历史；
- 想找一张旧壁纸，不用改文件名、不用搬文件夹，也能一眼认出来；
- 想回顾一段开发经历，能从项目找到仓库、RVC 模型、输出音频与个人笔记；
- 插拔移动盘不会让作品或足迹消失；
- 恢复数据时能准确知道“备份了什么、没有备份什么、哪些东西恢复成功”；
- 外部 AI 通过受控 MCP 操作档案，而 Looma 核心仍然安静、可靠、本地优先。

**最终原则：Looma 应当减少用户维护数字生活的工作量，而不是制造一份新的数字家务。**
